# Superflow CLI 统一评价体系

本框架用于回答三个问题：改动是否真的更好、为什么更好或更差、下一步应该改哪一层。
它适用于文档流水线、Skill、Hook、CLI、MCP、托管编排和安装升级。

## 评价维度

| 维度           | 核心证据                          | 典型指标                                                                                  |
| -------------- | --------------------------------- | ----------------------------------------------------------------------------------------- |
| 文档合同质量   | 来源追溯、冻结设计、门禁结果      | 澄清遗漏、coding-ready 通过率、实现歧义数                                                 |
| 交付正确性     | Host finding、测试报告、真实证据  | 首轮通过率、阻断数、关闭率、残留缺陷                                                      |
| 执行效率       | 事件、调用、里程碑和监督点        | 有效调用数、评审轮次、每调用里程碑、碎片返回、Host 唤醒数、有效/空闲监督点、无进展升级    |
| 时间与成本     | usage、active/wall time、状态区间 | Token/里程碑、活跃耗时、Host 评审等待、连接等待、用户控制等待、未归类等待、成本（可用时） |
| 自主性         | 用户输入与批准事件                | 人工指导、控制、预算/权限批准次数、可自主关闭比例、无效澄清次数                           |
| 恢复性         | 状态、指纹、重试和证据            | 休眠/重启恢复率、重复执行、证据丢失、临时故障恢复                                         |
| 规范一致与可移植   | 平台矩阵、干净环境验证            | Codex/Claude、中英文、OS、无个人绝对路径                                                  |
| 安装升级完整性 | doctor、指纹、安装清单            | CLI/MCP/Skill/Hook/脚本一致性、旧进程提示                                                 |

单个指标不能独立证明成功。速度提升但首轮通过率下降、Token 降低但人工介入增加，均不得
直接判为优化成功。

预算扩容、供应商切换、数据披露或权限批准属于可审计的人工介入，但应与人工编码、
业务澄清和暂停/恢复控制分开统计；否则“零人工介入”会掩盖真实运营成本。
`human.message_received` 与恢复执行的 `human.guidance_resumed` 都归入人工指导，
不得只统计其中一种事件；Host 自动评审轮次则单列，不能冒充人工指导或零成本。

**慢不等于空转。** Executor 持续模型输出或工具活动期间，Host 应留在本地 wait，不能因耗时长
反复调用 status、启动嵌套监督 Agent 或扣减效率分。只有连续两个监督点都没有阶段推进或权威命令
完成时，才记一次“无进展升级”并唤醒 Host；模型持续输出本身不是有效里程碑。评价必须分别报告
Host 唤醒数、有效/空闲监督点和无进展升级次数；MCP 未持久化 Host 轮询事件时只能写“不可观测”，
不得把未观测到误报为零轮询。

## 每次优化的最小评价记录

1. **问题证据**：来自哪些运行事件、finding、日志或用户反馈。
2. **责任层判断**：应改文档、门禁、Host、Executor、Runner、适配器还是安装器。
3. **基线**：改动前版本、任务类型、调用数、评审轮、耗时、Token、人工介入和终态。
4. **变更假设**：预期改善哪个指标，不能牺牲哪些指标。
5. **代表性实例**：每个独立优化至少一个可重复实例；复杂功能同时覆盖完整文档任务和
   口头最小合同，但不要求每次业务任务重跑框架认证。
6. **结果**：相同口径的前后数据、异常、finding 与证据路径。
7. **结论**：有效、部分有效、无效或回归，并解释原因。
8. **下一步与回滚条件**：明确该改哪一层；触发什么情况必须回滚。

## 评价分层

- **受影响验证**：单元测试、协议/Schema、双语一致性和对应冒烟实例；每次改动必做。
- **任务级真实验收**：按冻结文档完成编码、启动、API/页面/数据库证据与清理；用于验证
  一次真实交付，不用来证明整个框架普遍有效。
- **框架认证**：跨任务类型、宿主、语言、休眠/恢复和故障注入的基准集合；发布重大
  编排变更前执行，不得为每个业务任务重复。

## 自动评价与人工评审边界

`superflow eval` 从落盘状态、事件、用量、review finding，以及 Runner 已确认的项目内验收
报告计算单 Run 的事实指标，并输出“结论、为什么、下一步”。项目报告只可由
`review-facts-*.json` 的权威 `workspace.changedFiles` 引用，且必须是项目根目录内的
`*report.md`；不得扫描源码、越出项目目录或从无效 Agent 交付元数据推断。它可以发现调用
碎片、等待过高、无里程碑、首轮阻断和整改未收敛；不能证明代码、架构或业务语义正确。

等待只可按落盘状态区间归因为 Host 评审、供应商/连接、暂停/用户控制；其余非活跃时间必须
标为“未归类等待”，不得臆测为 Agent 空转或电脑休眠。Host 用量未由宿主提供时必须明确显示
“不可得”，不得将 Executor Token、缓存读取或供应商美元估算伪装成双 Agent 总成本。

Host 必须独立评审源码、设计一致性和测试证据。自动建议必须按责任层归类：

- 重复实现/测试遗漏 → 改 `design.md`、`tests.md` 或文档 Skill；
- 可确定格式/状态/证据错误 → 改 Hook、preflight 或门禁；
- 代码正确性/架构风险 → Host finding；
- 调度、等待、恢复、通信错误 → 托管状态机或协议；
- 平台差异 → Host adapter；安装缺失 → 安装升级闭环。

## 趋势评价口径

多任务比较必须固定版本、任务复杂度、Host/Executor、环境和有效调用定义。至少报告样本数、
成功率、首轮通过率、平均及 P50/P95 有效调用/评审轮/活跃耗时/墙钟耗时、Token/里程碑、
人工介入率、恢复成功率和主要 finding 类别。供应商临时拥塞及连接传输失败、休眠和等待需
单独标注，不能混入研发有效耗时或有效预算。供应商美元成本仅在其声明可信计费口径时作参考；
跨模型趋势默认以 Token、有效调用和里程碑口径比较。

`superflow eval <taskPath...> --summary` 只读汇总传入任务的落盘 Run，输出样本数、交付就绪率、
首轮评审通过率、有效调用和每里程碑 Token 的平均/P50/P95，以及人工介入和监督统计。它不自动
判定样本可比性；操作者必须先固定版本、任务复杂度、Host/Executor 和环境，不能混入不同模型、
不同任务档位或不同版本后宣称成本趋势。

样本不足时明确写“观察”，不得写成普遍结论。

## 固定交付验证与按差异选择维护验证

**以后每次完善 Superflow，交付前执行唯一完整入口：**
`npm run --silent verify:changed -- --full --json --report /tmp/superflow-verification/summary.json`。
先记录问题证据、责任层、基线和假设，再实现并观察正反例，最后记录实际结果与回滚条件；
不另建 Skill、Hook、菜单或长期验证状态来重复该 owner。

日常修改仍可运行 `npm run --silent verify:changed -- --base <ref> --plan --json` 查看确定性
计划，再去掉 `--plan` 执行窄验证；未知/共享源码、安装、包元数据与 Agent 规则影响
保守回退完整验证。只有已验证的隔离叶节点使用窄映射，不凭相似文件名猜测试 owner。
`--language zh|en` / SUPERFLOW_LANG 控制输出。计划预览不执行检查，不代表验证成功。

完整入口顺序执行全局/托管设计门禁、类型检查、Lint、严格技能审计、**一次完整 npm test**、
构建和真实 npm 包安装冒烟。正常流程基线唯一声明在 `scripts/verify-changed.mjs`；复用
同一次 Vitest JSON 报告，必需 suite 缺失、空执行、失败或任一断言跳过均不通过。
基线覆盖双宿主/双语/项目与全局隔离安装、完整合同与真实 OpenSpec 严格校验、
docs→design→implement 状态迁移、真实七个子门禁生成 Coding Ready 凭证、缺合同阻断、
有效实施续跑、内容漂移失效、恢复和升级；不得手写成功凭证代替完整正链。

工具基线为 Node 20/24、Python 3.12 和 OpenSpec 1.14.1。缺少工具应明确失败，不能跳过。
OpenSpec 可用独立临时 prefix 安装并将其 `node_modules/.bin` 加入 PATH；不要求全局安装。
CI 使用同一 `--full --json` 入口，在 Linux/macOS × Node 20/24 上运行，失败也保留报告
和详细日志；准备阶段失败保留同一入口的 NOT_RUN 预览（success:null）与 setup 日志，
checkout 本身失败只保留 GitHub 原生日志。CI 配置不等于矩阵已经实际运行，
Windows 或真实模型行为不得据此宣称通过。

每次执行的临时证据使用独占目录，`--report` 只指定最终汇总文件。逐检查记录
PASS / FAIL / NOT_RUN，失败立即停止并保留真实退出码，其余项明确未执行；预览成功状态为空。
完整执行前后核验源码、测试、规范资产、脚本与配置未变化；漂移则本次失败，不自动重跑。
构建输出只在本次临时输入/输出指纹匹配后打包，避免陈旧 dist 和重复 prepack 构建。
真实 tarball 安装到仓外干净 consumer，隔离用户目录和 Git/npm 配置，复用既有 CLI/部署
owner，不链接源码仓、不操作真实宿主、不以 dry-run 冒充安装；结束清理 consumer 后才报告通过。
CLI 只在正常成功命令后检查升级，帮助/版本退出不启动后台 npm；自动化设置
`NO_UPDATE_NOTIFIER=1`，`CI=1/true` 也禁用升级提示，避免遗留网络子进程。

详细子命令日志走 stderr，JSON stdout 可直接解析。这个入口证明确定性流程和安装事实，
不替代 Agent 的业务充分性评审、任务真实验收或发布流程。若漏执行/跳过基线仍获通过、
报告与产物不是同次输入、未知资产被覆盖或安装触及真实全局配置，应撤回对应改动，
保留仓外失败证据，修复后重新运行同一完整入口。

## 日常 Flow Owner 的持续交付评价

问题证据：实战中阶段汇报提前结束、可修复失败反复索取继续授权、上下文紧张被当成
交付终点。源码对比还发现普通入口混用托管 Host 只读限制、Prompt 强制团队和验证失败
停等规则。确定性前测中，已有实现 Prompt 仍返回 handoff；普通 Owner 模式无法进入
既有验证阶段。责任层为 Agent 执行合同、既有 SDD 路由及恢复，不是新托管调度器。

假设：扩展现有 superflow/build/verify 的责任与 `build_mode: owner`，保留合同、状态、
独立评审、真实验收和授权边界，可以减少阶段间人工接力。代表实例覆盖双宿主/双语/
项目与全局安装、缺 Prompt 与有效 Prompt、manual 模式、旧执行模式、verify-fail 回流、
完整 Coding Ready 正链，以及只文档、环境阻塞与上下文恢复的 Agent 情景。
独立复核发现 Quick 规格摘要与进度混写冲突，改为同目录报告保存执行进度；英文风险
词保持原语义。Quick 报告显式纳入任务文件范围，未知脏文件仍阻断；真实 CLI 回归还
修复所选项目相对 spec 读写基准及有效 in-progress/done 的续跑提示。
无风险 scale 的正常空匹配先复现非零退出，再修为零计数；读取错误
仍失败，不放宽风险词或必测门禁。

前后命令、情景行为、真实合成任务、全量及打包安装结果保存在本次仓外证据目录；
单样本只能证明该样本闭环，不能推断真实模型总体服从率、后台续跑或 Windows 实机。
若普通请求创建托管 Task、文档越权编码、模式静默切换、必测缺失被报完整交付、
未知资产受损或新增平行状态，则撤回对应变更，保留证据并重新验证。

## Multica 机制吸收验证（2026-10-12）

问题证据：额度错误可能被刷新 token/403 外观遮蔽；失败调用遗漏用量；累计未知值可在后续调用复活；Claude 临时重试序列混入重复事件；测试只隔离 HOME 无法约束 Windows profile；版本号不能说明启动构建来源。基线为本轮之前 Comet 验证的 104 文件、855 项通过。

变更假设：扩展既有错误分类、调用证据、进程监督、fixture 环境和构建末步，可以改善这些确定性事实而无需新增 Skill、Hook 或状态机。独立复审发现 adapter 与 Runner 分类串层不一致，已要求统一既有 failure owner，覆盖永久 usage-limit 与暂时 concurrent-limit 正反例。

代表实例：403 usage-limit 不抵扣、不自动重试；失败物理调用计一次用量；known→unknown→known 与 unknown→success 保持累计未知；重复 attempt、跨 session、政策拒绝及同 chunk 迟到成功；干净/脏/嵌套/非 Git 构建来源；外层环境恢复和 TMP/TEMP 保留。新回归先观察失败再通过，不用真实业务数据库或外部模型调用替代 fixture 验证。

结论边界：本轮证明机制和安装行为，不证明真实供应商稳定性、研发成功率或 Windows 实机兼容性；未复制 Codex app-server Guardian 或 excludeTurns。若分类错误抵扣、重复用量、未知复活、环境泄漏、构建来源冒认或 stale gate 改变，应撤回对应实现并保留原始失败证据，修复后重跑代表案例及最终全量门禁。

最终结果：106 个测试文件、908 项全部通过；完整编译检查、ESLint、设计与托管门禁、Skill Registry 严格审计通过（16/16，英文镜像缺口 0）。独立五维复审发现并关闭两项分类问题。npm 包含 404 文件，临时 consumer 安装成功；真实 MCP 进程验证启动来源未知、元数据替换不改启动身份、安装代码变更拒绝旧进程。未做 Windows 实机、真实外部模型或业务数据库验证；没有提交、发布或替换全局 npm CLI。日志：`/tmp/superflow-multica-verification-final.log`。

## 0.5.22 全局链路复核

基线为 Multica 吸收后的 106 文件、908 项测试。隔离复现发现：代码块 TODO/CASE_PASS 在 delivery 中误拒，正文 FAIL 被归档示例 PASS 掩盖，原生 OpenSpec 入口可绕过 SDD 收口；单平台更新被登记项目扩大为另一宿主；MCP 纯资产更新不失效、后台 PID 复用可误杀。责任分别落在规范 lint/既有归档门禁、Skill Registry 路由、更新目标解析及运行时服务 owner。

假设：共享正文事实源、明确 SDD 入口边界、过滤所选平台、补齐指纹闭包与 OS 身份/启动握手，可以关闭这些断点而不增加平行 Skill、Hook 或 Task/Run 状态机。代表性正反例包含真实正文 TODO/FAIL、代码块示例、BLOCKED 文档冻结、已移动归档恢复、单/双平台更新、纯资产替换、合法服务复用、历史未知身份、PID 复用与启动身份观测失败。新增回归先 RED 后 GREEN；外部模型服从率和 Windows 实机不由这些 fixture 证明。

回滚条件：误放正文 FAIL、误拒合法关闭、扩大平台写入、失去旧 MCP 过期检测、停止未核验进程、启动失败后领取任务或新增调用浪费。出现时撤回对应 owner 的改动并保留原始证据，修复后重跑关联正反例和发布完整门禁。

最终稳定源码结果：107 个测试文件、968 项全部通过；编译检查、ESLint、全局/托管设计门禁及严格 Skill 审计通过。独立五维复审复现并关闭双向启动确认、中文关闭兼容、历史 Blocked 豁免问题；实际自建 Node 进程覆盖合法 ready、异常退出和活锁冲突。完整日志：`/tmp/superflow-0.5.22-verification-final.log`。构建、打包和发布产物以 0.5.22 annotated tag 的发布记录为准。

## 技能入口与命名收敛（2026-10-13）

问题证据：用户无法从菜单确认总入口及所属产品；16 个正式技能混用 Superflow/OpenSpec 前缀，docs/design/implement 职责难以区分，两个归档入口要求用户理解状态文件。接口变更标注还由独立依赖复制器安装，未纳入 Registry。责任层为 Skill 合同、宿主展示和安装升级；不改变 Task/Run 状态机、三个 JSON 协议或业务验收策略。
