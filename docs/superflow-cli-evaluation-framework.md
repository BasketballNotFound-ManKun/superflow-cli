# Superflow CLI 统一评价体系

本框架用于回答三个问题：改动是否真的更好、为什么更好或更差、下一步应改哪一层。它适用于文档
流水线、Skill、Hook、CLI、安装升级和受控交付流程。

## 评价维度

| 维度 | 核心证据 | 典型指标 |
| --- | --- | --- |
| 文档合同质量 | 来源追溯、冻结设计、门禁结果 | 澄清遗漏、Coding Ready 通过率、实现歧义数 |
| 交付正确性 | 评审发现、测试报告、真实证据 | 首轮通过率、阻断数、关闭率、残留缺陷 |
| 执行效率 | 事件、调用和里程碑 | 有效调用数、每调用里程碑、碎片返回 |
| 时间与成本 | 用量、活跃/墙钟耗时 | Token/里程碑、活跃耗时、等待占比、可信成本 |
| 自主性 | 用户输入与批准事件 | 人工介入、可自主关闭比例、无效澄清次数 |
| 恢复性 | 状态、重试和证据 | 重启恢复率、重复执行、证据丢失、临时故障恢复 |
| 兼容与可移植 | 平台矩阵、干净环境验证 | 受支持宿主、中英文、OS、无个人绝对路径 |
| 安装升级完整性 | doctor、版本、安装清单 | CLI/Skill/Hook/脚本一致性、旧进程提示 |

单个指标不能独立证明成功。速度提升但首轮通过率下降、Token 降低但人工介入增加，均不得直接判为
优化成功。

## 每次优化的最小评价记录

1. **问题证据**：来自事件、发现、日志或用户反馈。
2. **责任层判断**：文档、门禁、Agent、适配器还是安装器。
3. **基线**：版本、任务类型、调用数、耗时、Token、人工介入和终态。
4. **变更假设**：预期改善的指标及不可牺牲的指标。
5. **代表性实例**：每项独立改动至少一个可重复实例。
6. **结果**：相同口径的前后数据、异常、发现与证据路径。
7. **结论**：有效、部分有效、无效或回归，并解释原因。
8. **下一步与回滚条件**：明确责任层及回滚触发条件。

## 评价分层

- **受影响验证**：单元测试、协议/Schema、双语一致性和对应冒烟实例；每次改动必做。
- **任务级真实验收**：按冻结文档完成编码、启动、API/页面/数据库证据与清理；用于验证一次真实
  交付，不用来证明框架普遍有效。
- **框架认证**：跨任务类型、宿主、语言、重启恢复和故障注入的基准集合；发布重大流程变更前执行，
  不得为每个业务任务重复。

## 自动评价与人工评审边界

自动评价可以从落盘状态、事件、用量和评审发现计算事实指标，并诊断调用碎片、等待过高、无里程碑
和整改未收敛；它不能证明代码、架构或业务语义正确。

自动建议须按责任层归类：重复实现或测试遗漏进入文档；可确定格式、状态或证据错误进入 Hook 或
门禁；代码正确性和架构风险由 Agent 评审；平台差异进入适配器；安装缺失进入安装升级闭环。

## 趋势评价口径

多任务比较必须固定版本、任务复杂度、宿主、环境和有效调用定义。至少报告样本数、成功率、首轮
通过率、平均及 P50/P95 有效调用/活跃耗时/墙钟耗时、Token/里程碑、人工介入率、恢复成功率和
主要发现类别。样本不足时明确写“观察”，不得写成普遍结论。
