# Superflow CLI 统一评价体系

本框架用于回答三个问题：改动是否真的更好、为什么更好或更差、下一步应该改哪一层。
它适用于文档流水线、Skill、Hook、CLI、MCP、托管编排和安装升级。

## 评价维度

| 维度           | 核心证据                          | 典型指标                                                                                  |
| -------------- | --------------------------------- | ----------------------------------------------------------------------------------------- |
| 文档合同质量   | 来源追溯、冻结设计、门禁结果      | 澄清遗漏、coding-ready 通过率、实现歧义数                                                 |
| 交付正确性     | Host finding、测试报告、真实证据  | 首轮通过率、阻断数、关闭率、残留缺陷                                                      |
| 执行效率       | 事件、调用、里程碑和监督点        | 有效调用数、评审轮次、每调用里程碑、碎片返回、Host 唤醒数、有效/空闲监督点、无进展升级    |
| 时间与成本     | usage、active/wall time、状态区间 | Token/里程碑、活跃耗时、Host 评审等待、连接等待、用户控制等待、未归类等待、成本（可用时） |
| 自主性         | 用户输入与批准事件                | 人工指导、控制、预算/权限批准次数、可自主关闭比例、无效澄清次数                           |
| 恢复性         | 状态、指纹、重试和证据            | 休眠/重启恢复率、重复执行、证据丢失、临时故障恢复                                         |
| 兼容与可移植   | 平台矩阵、干净环境验证            | Codex/Claude、中英文、OS、无个人绝对路径                                                  |
| 安装升级完整性 | doctor、指纹、安装清单            | CLI/MCP/Skill/Hook/脚本一致性、旧进程提示                                                 |

单个指标不能独立证明成功。速度提升但首轮通过率下降、Token 降低但人工介入增加，均不得
直接判为优化成功。

预算扩容、供应商切换、数据披露或权限批准属于可审计的人工介入，但应与人工编码、
业务澄清和暂停/恢复控制分开统计；否则“零人工介入”会掩盖真实运营成本。
`human.message_received` 与恢复执行的 `human.guidance_resumed` 都归入人工指导，
不得只统计其中一种事件；Host 自动评审轮次则单列，不能冒充人工指导或零成本。

**慢不等于空转。** Executor 持续模型输出或工具活动期间，Host 应留在本地 wait，不能因耗时长
反复调用 status、启动嵌套监督 Agent 或扣减效率分。只有连续两个监督点都没有阶段推进或权威命令
完成时，才记一次“无进展升级”并唤醒 Host；模型持续输出本身不是有效里程碑。评价必须分别报告
Host 唤醒数、有效/空闲监督点和无进展升级次数；MCP 未持久化 Host 轮询事件时只能写“不可观测”，
不得把未观测到误报为零轮询。

## 每次优化的最小评价记录

1. **问题证据**：来自哪些运行事件、finding、日志或用户反馈。
2. **责任层判断**：应改文档、门禁、Host、Executor、Runner、适配器还是安装器。
3. **基线**：改动前版本、任务类型、调用数、评审轮、耗时、Token、人工介入和终态。
4. **变更假设**：预期改善哪个指标，不能牺牲哪些指标。
5. **代表性实例**：每个独立优化至少一个可重复实例；复杂功能同时覆盖完整文档任务和
   口头最小合同，但不要求每次业务任务重跑框架认证。
6. **结果**：相同口径的前后数据、异常、finding 与证据路径。
7. **结论**：有效、部分有效、无效或回归，并解释原因。
8. **下一步与回滚条件**：明确该改哪一层；触发什么情况必须回滚。

## 评价分层

- **受影响验证**：单元测试、协议/Schema、双语一致性和对应冒烟实例；每次改动必做。
- **任务级真实验收**：按冻结文档完成编码、启动、API/页面/数据库证据与清理；用于验证
  一次真实交付，不用来证明整个框架普遍有效。
- **框架认证**：跨任务类型、宿主、语言、休眠/恢复和故障注入的基准集合；发布重大
  编排变更前执行，不得为每个业务任务重复。

## 自动评价与人工评审边界

`superflow eval` 从落盘状态、事件、用量、review finding，以及 Runner 已确认的项目内验收
报告计算单 Run 的事实指标，并输出“结论、为什么、下一步”。项目报告只可由
`review-facts-*.json` 的权威 `workspace.changedFiles` 引用，且必须是项目根目录内的
`*report.md`；不得扫描源码、越出项目目录或从无效 Agent 交付元数据推断。它可以发现调用
碎片、等待过高、无里程碑、首轮阻断和整改未收敛；不能证明代码、架构或业务语义正确。

等待只可按落盘状态区间归因为 Host 评审、供应商/连接、暂停/用户控制；其余非活跃时间必须
标为“未归类等待”，不得臆测为 Agent 空转或电脑休眠。Host 用量未由宿主提供时必须明确显示
“不可得”，不得将 Executor Token、缓存读取或供应商美元估算伪装成双 Agent 总成本。

Host 必须独立评审源码、设计一致性和测试证据。自动建议必须按责任层归类：

- 重复实现/测试遗漏 → 改 `design.md`、`tests.md` 或文档 Skill；
- 可确定格式/状态/证据错误 → 改 Hook、preflight 或门禁；
- 代码正确性/架构风险 → Host finding；
- 调度、等待、恢复、通信错误 → 托管状态机或协议；
- 平台差异 → Host adapter；安装缺失 → 安装升级闭环。

## 趋势评价口径

多任务比较必须固定版本、任务复杂度、Host/Executor、环境和有效调用定义。至少报告样本数、
成功率、首轮通过率、平均及 P50/P95 有效调用/评审轮/活跃耗时/墙钟耗时、Token/里程碑、
人工介入率、恢复成功率和主要 finding 类别。供应商临时拥塞及连接传输失败、休眠和等待需
单独标注，不能混入研发有效耗时或有效预算。供应商美元成本仅在其声明可信计费口径时作参考；
跨模型趋势默认以 Token、有效调用和里程碑口径比较。

`superflow eval <taskPath...> --summary` 只读汇总传入任务的落盘 Run，输出样本数、交付就绪率、
首轮评审通过率、有效调用和每里程碑 Token 的平均/P50/P95，以及人工介入和监督统计。它不自动
判定样本可比性；操作者必须先固定版本、任务复杂度、Host/Executor 和环境，不能混入不同模型、
不同任务档位或不同版本后宣称成本趋势。

样本不足时明确写“观察”，不得写成普遍结论。
