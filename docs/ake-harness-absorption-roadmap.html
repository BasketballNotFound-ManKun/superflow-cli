把成熟做法吸收成自己的工程能力。

这份文档把 ake-harness 的研发能力拆成可验证的吸收单元。每一项都记录当前基线、预期收益、代表性例子、验证标准、回滚条件和是否应进入 Superflow 主流程。

核心取舍

优先治理 Skill 和评审编排，再补轻量 Java 护栏；状态机继续负责流程状态，代码地图继续作为定位器，暂不引入 qgate 全套裁决系统。

Skill Contract / Registry

P0
主要参考：ECC 的分层 Skill / path-scoped rules；ake-harness 的 description 审计和单一事实源。
  • 吸收：每个 Skill 声明 owner、trigger、not-trigger、输入、输出、状态 owner、近邻互斥和测试。
  • 例子：新增一个 `superflow-xxx` 时，自动发现是否和 clarify/docs/implement 重叠。
  • 验证：重复触发词、缺中英文镜像、未接入安装、孤儿 Skill、多个状态 owner 均能被确定性报告。
  • 回滚：只读报告，不改变已安装 Skill；误报率超过 5% 时先撤销阻断，仅保留 advisory。

确定性代码评审编排

P0
主要参考：ake-review / GSD code-reviewer。
  • 吸收：diff 文件枚举、path-scoped rules、Java/XML bundle、coverage、风险档位、reviewer 四态。
  • 例子：修改 `OrderMapper.xml` 和 `OrderMapper.java` 时必须组成同一评审单元；漏掉一个文件直接显示 coverage 缺口。
  • 验证：100% 改动文件被 included/excluded 解释；每条 finding 有 file:line；BLOCKED 不得拿部分报告进入 triage。
  • 回滚：评审只读 advisory，不改现有 Coding Ready 门禁。

Quick Path + Quick Spec

P0
主要参考：ake-quick-dev。
  • 吸收：小任务窄门、`.sdd/tasks` 或轻量任务 spec、批准后实施、意图变化回 draft。
  • 例子：改一个已有校验方法可以走 quick；改 DB、公共 API、事务或跨模块必须升级完整 SDD。
  • 验证：窄门命中时输出 QUICK/STOP；未批准的 quick spec 不能写运行时代码；范围扩展能被识别。
  • 回滚：quick 路径失败只回到 full SDD，不修改现有 SDD 状态。

Java 写码时护栏

P0
主要参考：mybatis-injection-check、block-no-verify、commit-quality、java-edit-accumulator。
  • 吸收：Mapper `${}` 阻断、Git Hook 绕过阻断、提交密钥扫描、Java 编辑路径累积。
  • 例子：Agent 写入 `${userInput}` 时立即阻断；修改 10 个 Java 文件只在 Stop 编译一次。
  • 验证：安全探针 exit 2；合法白名单不误报；Stop 编译覆盖 Maven/Gradle 多模块。
  • 回滚：Java 特定规则仅对命中路径生效，异常时 fail-open 的观察 Hook 保持不阻断。

试点结果（2026-09-23）：已接入真实 PreToolUse、PostToolUse、Stop 入口；虚构多模块仓库验证危险插值、白名单、Git 绕过、暂存密钥、十次编辑一次 Maven 编译、Gradle 多模块一次编译、失败重试和缺工具 UNKNOWN。基线：这些 Java 护栏缺失；变更后危险输入 exit 2，安全样本 exit 0，十次编辑只产生一次构建调用。证据：test/unit/java-guard-hooks.test.ts、全量测试与双端 doctor。该项为 Hook 事实验证，不用任务评分代替安全探针；若出现合法 Mapper 误拦或 Stop 反复构建，应回滚对应规则。

行为不变简化收尾

P0
主要参考：ake-simplify。
  • 吸收：只看本次 diff、Chesterton's Fence、一次一项、每项独立验证、和功能改动分开提交。
  • 例子：删除重复 helper 前先确认所有消费者和错误行为不变，测试不改一字仍通过。
  • 验证：每处简化都有原有测试/编译绿证据；触碰范围外代码直接 STOP。
  • 回滚：简化不产生行为差异时才保留，红灯直接恢复。

试点结果（2026-09-24）：以第四项虚构多模块 Java 护栏代码为样本，基线为 Git 命令解析在两处重复；只提取共同解析和子命令定位，未修改测试断言，原有 7 项 Hook 故障注入继续通过。收尾纪律写入现有中英文 verify 技能，没有增加新 Skill、状态或门禁。证据：assets/scripts/superflow-sql-sync-hook.py、test/unit/java-guard-hooks.test.ts；若原测试需改动或受影响范围扩张即回滚。

失败循环观测

P0
主要参考：loop-detection、circuit-breaker、session-reflection。
  • 吸收：同文件反复编辑、同工具连续失败、SessionEnd 状态清理；全部 fail-open。
  • 例子：10 分钟同一文件修改超过 5 次时提醒重审方案；工具 5 分钟失败 3 次时提醒分析原因。
  • 验证：状态按 session 隔离、有时间窗、SessionEnd 清理临时文件，不影响正常交互。
  • 回滚：只关闭提醒，不删除托管预算和停止条件。

试点结果（2026-09-24）：虚构会话连续编辑和工具失败样本中，基线没有原生 Hook 提醒；变更后第六次编辑和第三次连续失败各提醒一次，后续重复事件安静，成功调用清零失败序列，另一会话不受影响，过期记录与 SessionEnd 均清理。所有注入恒退 0。证据：test/unit/loop-observer-hook.test.ts、双端安装配置与 doctor；若正常任务误报或 Hook 开销不可接受，移除观察 Hook 即可，不触及托管预算。

CONTEXT / ADR 三条件

P1
主要参考：mattpocock domain-modeling；ake-domain-model。
  • 吸收：统一术语进入 `CONTEXT.md`；真正难逆转且有权衡的决定进入 ADR。
  • 例子：“站点”“场站”“充电站”统一成一个规范词；新增表还是扩旧表的取舍留 ADR。
  • 验证：术语表不含实现细节；ADR 必须能找到备选方案和后果；普通易逆转决定不产生 ADR。
  • 回滚：只提议不阻断，不把 ADR 变成额外审批流。

试点结果（2026-09-24）：新增只读 superflow context-audit，对虚构“站点存储策略”需求验证了业务术语、完整 ADR、实现细节误入术语表、缺字段 ADR 和无 ADR 普通需求五种结果。完整样例 PASS；错误样例报告修复项；普通需求仅 warning 且 exit 0。证据：test/unit/context-audit.test.ts 与 CLI JSON 输出。该审计不写状态、不替代 design.md；若术语误报或目录扫描扩张，回滚为 advisory 输出。

Seam / Design-It-Twice

P1
主要参考：mattpocock codebase-design；ssd-codebase-design。
  • 吸收：把测试 seam、删除测试、接口是否为真实测试面写进 technical design。
  • 例子：先比较“改调用方”与“在 adapter seam 收口”两种方案，再冻结较小爆炸半径的一种。
  • 验证：关键接口至少有两种方案记录；测试不穿透同一实现内部；复用点有源码证据。
  • 回滚：只增强设计模板，不替换现有 OpenSpec design.md。

试点结果（2026-09-24）：已把 Design-It-Twice 卡片接入中英文 superflow-design 和 technical design 模板，要求方案 A/B、seam/adapter owner、真实测试面、复用证据、后果和明确选择；“只改名”会被要求重做。验证为文档契约检查、构建与全量测试；不新增状态或审批门禁。

文档落位与策展

P1
主要参考：doc-placement-warn、ake-doc-curator。
  • 吸收：新建 Markdown 时提醒落位；doctor 事后盘点；按 obsolete/redundant/trivial/active 分诊。
  • 例子：临时测试报告进入任务目录，而不是散落在仓根或 `docs/` 顶层。
  • 验证：提示 Hook 恒退 0；删除和合并必须逐条确认；每个判定带年龄、引用或锚点证据。
  • 回滚：只提示，不自动移动、删除或合并文件。

试点结果（2026-09-24）：新增落位提醒 Hook 与 superflow docs-audit。虚构文档样本验证仓根新建 Markdown 提醒且 exit 0、已有文件静默；策展报告采集年龄、失效代码锚点、入链数并标记 obsolete/trivial/current，绝不删除文件。证据：test/unit/docs-audit.test.ts；误报时移除提醒 Hook，不影响文档和托管状态。

评审回应纪律

P1
主要参考：ake-review-response。
  • 吸收：先验证评审意见，再决定修复、反驳、延后或忽略；项目约定类问题确认后回写规则。
  • 例子：评审说“应该改成缓存”时，先核对请求量、现有缓存和设计边界，不直接附和。
  • 验证：每个 finding 有证据和处置桶；规则回写需要显式确认；不会因 reviewer 语气自动改变严重度。
  • 回滚：只影响评审行为，不改变代码门禁。

试点结果（2026-09-24）：已把先通读、源码核实、技术性反驳、逐项验证、YAGNI 调用点检查和规则回写确认接入中英文 superflow-verify。虚构“把单调用适配器泛化成缓存层”评审意见按有效/错误两种分支核对；没有第二调用方时保持最小实现，规则不自动写入。该项为行为纪律，不新增状态或 Hook。

BMAD 选择性职责路由

P1
主要参考：BMAD persona/routing；Superflow 已有 Host/Executor/Reviewer。
  • 吸收：只明确能力 owner、入口和互斥边界，不引入 Amelia/John/Murat 菜单。
  • 例子：Host 负责目标和评审，Executor 负责实现，Runner 负责状态和证据；Skill 不自动越权。
  • 验证：每个状态和 artifact 只有一个 owner；角色切换显式；没有重复路由和嵌套 Supervisor。
  • 回滚：保留现有 Superflow 三角色协议，不增加 persona 状态层。

试点结果（2026-09-24）：已在中英文 pipeline 中补充 Host/Executor/Runner owner 矩阵和互斥边界。虚构“Host 直接改代码、Executor 改合同、Runner 判断业务语义、嵌套 Supervisor”四个反例均按规则回到正确 owner；无新增状态机或 persona 层。

地图检索对照实验

P2
主要参考：OpenAI harness engineering、Aider、Agentless、LocAgent；当前使用 Understand Anything 定位。
  • 吸收：只做渐进披露、文件/符号骨架和任务相关召回实验，不替换现有状态机。
  • 例子：比较“完整图谱”“任务 Top-K”“目录+符号骨架”三种上下文，测跨模块入口召回。
  • 验证：同一任务集比较 Recall@K、误导率、工具调用、token 和最终实现正确性。
  • 回滚：实验不通过就保留 Understand Anything locator，不引入第二套持久地图。

试点结果（2026-09-24）：新增只读 superflow map-audit，对虚构 Controller/Mapper 图谱输出 full、任务 Top-K、目录/符号骨架三种规模；图谱缺失时明确 fallback，不伪装召回，不修改现有图谱。证据：test/unit/map-audit.test.ts。该项仅验证上下文形态，尚未宣称 Recall@K 或最终实现质量提升。

全仓清理候选扫描

P2
主要参考：ake-cleanup-scan、ake-deepen。
  • 吸收：只读枚举全仓重复、过度防御、浅模块和热点，报告后停止。
  • 例子：扫描消费方仓库时列出可删除候选，但不在扫描阶段自动改业务代码。
  • 验证：覆盖清单无漏项、每个候选有 file#symbol、消费者证据、行为不变量和执行路由。
  • 回滚：报告临时保存，用户选中后才路由到 quick/SSD/codemod。

试点结果（2026-09-24）：新增只读 superflow cleanup-audit，对虚构重复 Service、TODO 热点和大文件输出候选、机械证据与 simplify/review/manual 路由；命令明确 modified=false，不会自动删除或重构。证据：test/unit/cleanup-audit.test.ts。

qgate 全套静态分析裁决

暂缓
主要参考：ake-static-analysis-init、qgate、项目锁定护栏。
  • 暂缓原因：涉及任务快照、分析器 adapter、baseline、policy、缓存、控制面和故障注入，复杂度远超当前缺口。
  • 未来触发：现有 Hook/验证反复漏掉可机械识别的 Java 缺陷，并且有稳定误报/漏报证据。
  • 验证：先做单一 Java 项目预览、故障注入、快检预算和 UNKNOWN 语义实验。
  • 回滚：不影响现有 Superflow docs/verify/managed 状态机。

效果验证协议

功能测试证明“机制能运行”；同题对照才判断“吸收后更有效”。试点前冻结题目、模型、代码快照、预算和评分规则。

样本怎么选

至少覆盖：低风险单文件修复、Java + Mapper 变更、跨模块 API/DB 变更、旧代码库评审、失败工具循环，以及 Codex/Claude 双端安装。每类保留吸收前的基线和吸收后的同题结果。

效果怎么判

先看正确性：漏评文件、错误高可信 finding、越权改动、未验证却报 PASS 均为 No-Go。再看效率：有效调用、输入 token、用户确认次数和等待时长；质量改善若伴随明显额外成本，需说明是否值得。

指标建议通过线失败后的动作
交付正确性真实任务的首轮评审通过率不低于基线；新增机制不得产生错误高可信结论停用该规则或降为 advisory，回查证据与适用范围
覆盖与可恢复性改动文件覆盖 100%；冻结合同变更能使旧交付资格失效；换会话可从磁盘恢复先修确定性协议，再扩大试点
人工负担明确的小任务不增加无效确认；重大 owner 决策只询问一次并记录合并重复检查点，保留真正决策点
时间与成本固定样本下分别报告调用数、token、活跃耗时和等待；不以单个数字宣称优化质量收益不足以覆盖成本时回滚或缩小触发范围
安装一致性中英文、Codex/Claude、干净安装和升级后均发现同一能力闭包暂停默认分发，先修安装闭环

每个吸收单元的完成定义

不是“Skill 文件写出来”就算完成。必须同时有机制、消费方、验证和回滚证据。
