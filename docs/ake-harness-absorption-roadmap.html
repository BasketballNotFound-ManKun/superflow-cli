A01 · 迁移必须证明“属于我们且未被用户改写”

P0提议，未实施
吸收理由
现有迁移只有名称/标记，缺少 ECC 所倡导的资产所有权和受控执行层。先收紧能自动删除的集合，防止治理工具本身损害项目。
方案推演
安装时记录规范路径、host/scope、来源版本、已装内容哈希与安装方式 → 审计 current/planned/user-modified/unknown → 生成同一份 plan 供预览和执行 → apply 前重验源文件指纹 → 单事务备份与原子替换。新旧 Hook 逐项说明替代能力，命令附带额外子命令时整个条目保留；旧版无 manifest 的只读报告。
复用 / 不选
扩展 hook-migration.ts、state.ts、platform/fs.ts，不复制 ECC 安装引擎。不能因“有备份”就删除来源不明资产；也不把存在一个 ake 标记视作该目录所有文件均未改写。
实例与验收
虚构同名自定义 Hook、官方 Hook 本地改写、混合命令、重复更新、缺脚本、被中断写入、父目录软链。拟定：自定义/未知内容零字节改变；不完整替代零自动删除；重复 apply 不写配置；备份可恢复到原始哈希；失败不留成功标记。
成本 / 回滚
增加每个受管资产的哈希读取与少量清单数据，不新增常驻进程。任何误删或 plan/apply 漂移即停止自动迁移，回退只读审计。ECC 设计文档是参考，机制需由本仓试点证明。

来源：ECC 安装设计、ECC 旧安装所有权与保留策略。

A02 · 用真实宿主合同补齐 Hook / MCP 适配

P0提议，未实施
吸收理由
相同脚本可被两个宿主安装，不等于事件、payload、阻断输出和超时语义兼容。现有 doctor 数量判断和字符串路径改写不足以认证。
方案推演
为支持的宿主版本维护 capability 表（event / matcher / 输入字段 / 输出 schema / timeout）→ 在边界归一化为内部事件 → 现有规则计算 allow/block/advisory → adapter 输出宿主协议。doctor 对比唯一事件+matcher+命令+哈希，并区分 configured/trusted/observed；拿不到 trust 信息写 unknown，不代签信任。
复用 / 不选
沿用 HOOK_MAP、manifest、现有脚本；先改高风险入口，避免大一统重写。复用 Zod 4 派生 JSON Schema，同时保留宿主 strict 与内部可选字段差异；Inspector 仅用于隔离协议探针。
实例与验收
普通 Read、shell、Edit、MultiEdit、apply_patch、非 SDD 子目录、root 含空格、Windows 路径、缺 Python/Java、损坏 JSON、Stop 重入与总超时。拟定：支持项实际触发一次；未知事件不宣称生效；只读场景无协议错误；危险场景能阻断并可恢复；doctor 不因堆积重复项而通过。脚本输入注入和真实 Codex/Claude 端到端两种证据分别记录。
成本 / 回滚
无须新增每次模型调用。短 Hook 预算先测 p50/p95，编译等耗时工作独立预算；协议回归就禁用受影响适配版本并明确降级，不静默放宽确定性阻断。

来源：OpenAI Hooks、Claude Hooks、Zod Schema、MCP Inspector。上游现行文档不代表已安装历史版本，必须锁版本回放。

A03 · 用 Promptfoo 测“模型实际上做了什么”

P0提议，未实施
吸收理由
Registry 的字段存在检查和 CLI 的 nextSkill 断言不能证明 Claude 会调用正确 Skill。PLMP 的 Quick → ake 漂移是现成失败样本；现有 excellent 只衡量流程终态与效率。
方案推演
将脱敏后的失败场景冻结成 fixtures → 无增强/当前版/候选版同题对照 → 收集真实工具调用、产物位置和最终 diff → 用确定性断言判断框架归属与禁止副作用，再由独立评审判断质量。Promptfoo 可组织数据与报告，superflow eval继续统计 Run，不新增另一套托管裁决。
复用 / 不选
沿用当前 Skill Registry、Quick、语义评审和 Run 账本。先 8–12 个场景，每个每宿主重复 3 次，再决定扩大；不把“输出提到某技能名”当实际使用。官方教程对 Codex 的 skill-used 可由读文件推断，证据弱于工具调用；须加产物/轨迹核验，且使用本机允许的 Codex 技能来源，不照搬 .agents 安装路径。
实例与验收
API+鉴权 Quick STOP、普通文案非 DB、仅依赖旧变更、两个框架共存、用户明确切 ake、同名不同 namespace Skill。拟定：固定集未经授权跨框架创建产物为 0；有效任务完成率不低于基线；报告总样本数、错误路由率、人工介入、token/耗时与失败原文。少量全通过只称样本通过。
成本 / 回滚
仅开发/CI 按需调用模型，预算预先封顶；企业对话先脱敏，优先合成复现，不上传原日志。质量不升或成本明显上升时撤掉新提示。先复用实际宿主 CLI；必要时才增加 SDK provider，SDK 结果不可直接等同宿主 UI。

来源：Skill 对照指南、断言与指标。

A04 · 用 fast-check 验证状态组合，而非再造状态机

P1提议，未实施
吸收理由
已有大量状态测试值得复用；缺口在更长的操作组合、并发写入、异常恢复与随机路径。单个案例绿不证明组合不丢状态。
方案推演
用简化业务模型描述允许状态 → 生成 start/pause/resume/review/reopen/cleanup、install/update/uninstall 序列 → 实现与模型核对不变量 → 失败缩成最短步骤，保存 seed/replayPath。文件原子写入复用现有 helper；确有丢更新证据再加互斥，不先上数据库。
实例与验收
同时更新两个任务索引、评审前崩溃、临时文件残留、旧会话迟到结果、更新→卸载→更新。拟定：固定 seeds 至少 1000 序列，零未知资产改写、零预算负数、零重复终态、账本哈希链可恢复；模拟模型应更简单，不能复制实现自证。
性能补充
对 10³/10⁴/10⁵ 事件账本测追加与恢复。当前 lastEvent/regenerateProgress 全量读取是可见优化点；确认瓶颈后只改尾部读取与视图生成，保留原始账本和哈希，不默认引入 OTel/数据库。
成本 / 回滚
fast-check 仅 devDependency；初期限安装迁移和纯状态函数。随机失败必须可复现；模型误判或运行超过预算时缩小集合，不通过增大超时掩盖缺陷。

来源：fast-check 模型、缩减与重放。

A05 · dependency-cruiser + Knip，先守边界再拆大文件

吸收理由

效果怎么判

先看正确性：漏评文件、错误高可信 finding、越权改动、未验证却报 PASS 均为 No-Go。再看效率：有效调用、输入 token、用户确认次数和等待时长；质量改善若伴随明显额外成本，需说明是否值得。
