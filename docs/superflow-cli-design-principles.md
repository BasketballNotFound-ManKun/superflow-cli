# Superflow CLI 全局设计纲领

本纲领是 Superflow CLI 的最高维护约束。修改 CLI、Skill、Hook、脚本、安装升级或文档模板前
必须完整阅读；专项规则只能细化本纲领，不得冲突。

## 1. 产品定位

Superflow 不替代开发 Agent。它把需求来源逐步冻结为可追溯、低自由度、可执行的
OpenSpec/SDD 交付合同，并提供受控的研发交付流程。

## 2. 事实源与职责分层

事实源优先级为：用户确认和原始需求 → 冻结 OpenSpec/SDD 文档 → 项目工程规则 → 执行合同 →
运行证据。后层只能继承和执行前层，不得重新设计已冻结的选择。

- `proposal/spec/api/design/tasks/tests` 定义业务、技术实现和验收方案。
- `design.md` 冻结复用点、精确修改点、调用与数据流、事务并发、异常和实现顺序。
- `tests.md` 冻结环境、数据、启动命令、自动化命令、断言、清理和证据位置。
- 实现 Prompt 只压缩并继承合同，不创建第二套方案。

完整 Superflow 任务必须是低自由度交付；通用 Prompt 不得硬编码具体业务 API、SQL、数据库、
框架、并发或端到端测试策略。

## 3. Agent 判断与脚本裁决

脚本负责可重复、可证明、可离线重放的事实：Schema、文件、哈希、状态转换、进程身份、退出码和
结构化证据。Agent 负责需求含义、架构合理性、代码正确性、风险、测试充分性和整改优先级。

高风险且确定的规则不能只写在 Prompt 中，必须由 Hook、preflight 或最终门禁保障；开放式语义
判断不得伪装成正则门禁。门禁失败必须说明事实、修复入口和恢复方式。

## 4. 简单、复用与兼容

- 先搜索并扩展现有模块、Skill、脚本、协议和测试，避免平行实现。
- 优先最少状态；没有证据不得为未来扩展增加层、缓存、异步或补偿。
- 一个概念只有一个 canonical source（规范事实源）；派生资产由安装或生成流程同步。
- 协议和落盘格式须版本化、向后兼容、失败安全、可恢复且可审计。
- 中英文文档、Skill、Prompt、CLI 帮助和测试必须同步，语义不得漂移。

## 5. 安装与升级闭环

源码安装、npm 安装和自动升级必须部署同一完整能力闭包：CLI、Skill、Hook、脚本、文档和运行时
依赖。升级后必须可诊断当前版本和运行时；需要重启时，应明确说明原因和动作。

## 6. 评价驱动维护

任何工作流优化都必须遵循 `superflow-cli-evaluation-framework.md`：先记录基线和假设，再以代表性
实例冒烟或回归，最后比较交付质量、效率、成本、恢复性、人工介入和兼容性。不得只凭单轮体感、
单一耗时或 Token 数作出架构结论。

评价器只诊断可审计事实，不替代 Agent 的代码与架构语义评审。重复问题应放到正确层级：业务实现
和测试要求进入文档体系，确定性失败进入脚本门禁，语义问题进入评审清单。

## 7. 修改流程与完成定义

1. 阅读本纲领、评价框架和受影响专项规则。
2. 搜索现有实现，写明问题证据、责任层、变更假设和不改范围。
3. 采用最小改动，并同步中英文和受影响宿主。
4. 为每项独立优化准备代表性实例；执行受影响测试、全量测试、构建、Lint 和设计门禁。
5. 记录前后指标、异常、结论、剩余风险与回滚条件。
6. 若证据否定假设，回退或重新设计，不通过放宽测试或门禁宣称成功。

完成不等于“代码已写”。只有事实源一致、职责未串层、验证通过、安装闭环完整、评价可解释且无
未声明回归时，才可交付。
