# Superflow CLI 全局设计纲领

本纲领是 Superflow CLI 的最高维护约束。Codex、Claude 以及其他受支持的开发 Agent
修改 CLI、Skill、Hook、脚本、MCP、托管、安装升级或文档模板前，必须先完整阅读本纲领；
涉及托管时还必须阅读 `managed-work-design-principles.md` 和
`managed-agent-protocol.md`。专项规则只能细化本纲领，不得与其冲突。

## 1. 产品定位

Superflow 不是新的通用 Agent，也不替代 Codex 或 Claude。它提供两类能力：

1. 把需求来源逐步冻结为可追溯、低自由度、可执行的 OpenSpec/SDD 交付合同；
2. 用轻量双 Agent 托管把“研发执行—真实验证—独立评审—集中整改—交付”自动循环起来。

这两类能力支持三个彼此独立但可衔接的入口：只生成并评审文档；用户确认 Coding Ready
后从冻结 change/Prompt 启动托管；口头给出简单需求直接托管。第三种入口一旦出现会改变
实现方向的 API、数据、并发、跨仓或 owner 决策，Host 必须先升级到澄清/文档流程，不能
让 Runner 靠关键词猜方案，也不能让 Executor 临场补第二套合同。

Host 是任务目标、澄清、监督和评审的 owner；Executor 是编码、启动、测试和整改的
owner；Runner 只裁决确定性事实并持久化状态。不得启动嵌套 Supervisor CLI，也不得让
Runner 用字符串规则替代 Agent 的语义判断。

## 2. 事实源与职责分层

事实源优先级为：用户确认和原始需求 → 冻结 OpenSpec/SDD 文档 → 项目工程规则 →
托管执行合同 → 运行证据。后层只能继承和执行前层，不得重新设计前层已经冻结的内容。

- `proposal/spec/api/design/tasks/tests` 定义业务、技术实现和验收方案。
- `design.md` 必须冻结复用点、精确修改点、调用与数据流、事务并发、异常和实现顺序。
- `tests.md` 必须冻结环境、数据、启动命令、步骤、自动化命令、响应/数据库/日志断言、
  清理和证据位置。
- 实现 Prompt 只压缩并继承上述合同，不创建第二套方案。
- 托管只负责上下文冻结、调度、等待、证据、评审整改循环和终态交付。
- 口头简单需求可以生成最小执行合同；出现会改变方向的选择时必须交回 Host 澄清。

直述的 `engineering/sdd` 需求即使没有用户提供的 implementation prompt，也必须自动生成、
冻结并哈希一份**标准执行合同**后才可启动 Executor。它只约束源码核实、复用、资源所有权、
真实验收、清理、证据和澄清边界；涉及运行环境时还必须约束验收入口可移植、失败清理与
不得以宽泛替身伪造启动。直述并发需求只能要求确定性的非 5xx 业务冲突和一次持久化状态
转换，不编造具体 API、DB、事务或测试细节；这些细节仍应由项目文档或 Host 澄清冻结。
不得把“没有外部 Prompt”显示为“没有冻结合同”。

完整 Superflow 任务必须是低自由度交付：Executor 不应再决定“怎么编码”或“怎么测”。
具体 API、SQL、数据库、框架、并发和端到端测试策略不得硬编码进通用托管 Prompt。

## 3. Agent 判断与脚本裁决

脚本负责可重复、可证明、可离线重放的事实：Schema、文件、哈希、状态转换、进程身份、
命令退出码、结构化证据和协议兼容。Agent 负责需求含义、架构合理性、代码正确性、风险、
测试充分性和整改优先级。

高风险且可确定的规则不能只写在 Prompt 中，必须由 Hook、preflight 或最终门禁保障；
开放式语义判断不得伪装成正则门禁。门禁失败必须说明事实、修复入口和恢复方式。

## 4. 简单、复用与兼容

- 先搜索并扩展现有模块、Skill、脚本、协议和测试，避免平行实现。
- 优先同步事务和最少状态；没有证据不得为未来扩展增加层、缓存、异步或补偿。
- 一个概念只有一个 canonical source（规范事实源）；派生资产由安装或生成流程同步。
- 协议和落盘格式要版本化、向后兼容、失败安全、可恢复、可审计。
- Codex、Claude 的能力差异由适配层处理，不污染核心状态机。
- 中英文文档、Skill、Prompt、CLI 帮助和测试必须同步，语义不得漂移。

## 5. 安装与升级闭环

源码安装、npm 安装、Hook 自动升级必须安装同一完整能力闭包：CLI、MCP、Skill、Hook、
脚本、文档和运行时依赖。升级后必须可诊断当前版本与运行时指纹；需要宿主重启时，应在
当前会话明确通知原因和动作，不能静默使用旧进程。

## 6. 评价驱动维护

任何影响工作流或托管行为的优化，都必须遵循
`superflow-cli-evaluation-framework.md`：先记录基线和假设，再用代表性实例冒烟或回归，
最后比较交付质量、效率、成本、恢复性、人工介入和兼容性。不得仅凭单轮体感、单一耗时
或 Token 数作出架构结论。

评价器只诊断可审计事实，不替代 Host 的代码与架构语义评审。重复问题应放到正确层级：
业务实现/测试要求进入文档体系，确定性失败进入脚本门禁，语义问题进入 Host checklist，
通信与状态问题才进入托管编排。

## 7. 修改流程与完成定义

1. 阅读本纲领、评价框架和受影响专项章程。
2. 搜索现有实现，写明问题证据、责任层、变更假设和不改范围。
3. 采用最小改动，并同步中英文和三种受支持宿主。
4. 为每个独立优化准备一个代表性实例；执行受影响测试、全量测试、构建、Lint 和设计门禁。
5. 记录前后指标、异常、结论、剩余风险与回滚条件；人工批准必须区分指导、控制与预算/权限，
   不得把预算扩容漏记为零人工介入。
6. 若证据否定假设，回退或重新设计，不通过放宽测试、协议或门禁宣称成功。

完成不等于“代码已写”。只有事实源一致、职责未串层、验证通过、安装闭环完整、评价可解释
且无未声明回归时，才可交付。
