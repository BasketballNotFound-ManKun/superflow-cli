# Superflow CLI 全局设计纲领

## 默认原生托管边界（2026-10-19）

新建托管任务的 auto 默认解析为 `native`。托管是两个原生 Agent 的通信与监督层，
负责原始请求、会话、消息、证据引用、等待、恢复和评审，不接管 Agent 的研发策略。
技能、插件、子代理、记忆、原生权限及审批、上下文压缩与用户配置由 Agent CLI
自身加载；模型与推理仅在用户显式指定时传参，不能替用户静默覆盖。

技能命令与文档路径保持原文，不改造成另一份研发合同。自然回复由 Runner 封装进
现有执行消息，保持任务/轮次/会话与原文引用；收到回复不等于完成，Host 明确通过
前进度不晋升。评审 finding 与新用户指导同时交接，确认收到但失败的调用须续接
未完成信息，不能重放旧通过结论。用户显式工程约束继续有效。

原生模式不强制 JSON 研发输出、额外验收入口、Shell 写法或 curl 地址，不自动
授权 Git/生产操作，也不覆写用户原有权限。框架自己的合同、账本和会话元数据仍
由 Runner 独占；Agent 可只读交接，不能篡改这些内部状态。

原生预算默认不设硬上限，0 表示未设限；用户显式正值各自生效，包括调用、轮次、
时间、Token 和费用。未知用量不是零。独立工作区可以并行，重叠工作区按现有锁
和任务所有权排队；交付后的任务释放工作区，缺失的已停止旧登记隔离处理。

显式 quick/engineering/sdd/monitor 按各自现行合同执行；下文关于强工程合同、
受控工具及固定预算的条款只在适用档位生效。SDD 准入与续跑统一满足当前门禁，
不授予旧 READY 豁免。各路径共用 Task/Run、事件和三种 Agent 消息，不引入平行状态机。


本纲领是 Superflow CLI 的最高维护约束。Codex、Claude 以及其他受支持的开发 Agent
修改 CLI、Skill、Hook、脚本、MCP、托管、安装升级或文档模板前，必须先完整阅读本纲领；
涉及托管时还必须阅读 `managed-work-design-principles.md` 和
`managed-agent-protocol.md`。专项规则只能细化本纲领，不得与其冲突。

## 1. 产品定位

Superflow 不是新的通用 Agent，也不替代 Codex 或 Claude。它提供两类能力：

1. 把需求来源逐步冻结为可追溯、低自由度、可执行的 OpenSpec/SDD 交付合同；
2. 用轻量双 Agent 托管把“研发执行—真实验证—独立评审—集中整改—交付”自动循环起来。

这两类能力支持三个彼此独立但可衔接的入口：只生成并评审文档；用户确认 Coding Ready
后从冻结 change/Prompt 启动托管；口头给出简单需求直接托管。第三种入口一旦出现会改变
实现方向的 API、数据、并发、跨仓或 owner 决策，Host 必须先升级到澄清/文档流程，不能
让 Runner 靠关键词猜方案，也不能让 Executor 临场补第二套合同。

托管模式中，Host 是任务目标、澄清、监督和评审的 owner；Executor 是编码、启动、测试和整改的
owner；Runner 只裁决确定性事实并持久化状态。不得启动嵌套 Supervisor CLI，也不得让
Runner 用字符串规则替代 Agent 的语义判断。

### 日常交付的 Flow Owner

普通已授权任务默认由当前 Codex 或 Claude 担任 Flow Owner，连续负责实施、测试、
独立评审协调、整改和交付。Owner 可以编码与运行验证；托管 Host 的只读限制只在
托管模式生效。明确要求托管时仍使用原 Host/Executor/Runner 分工。

复用 superflow 唯一入口、既有 SDD phase、build_mode、任务与测试报告；普通 SDD
使用 `build_mode: owner`，不创建第二套 Task/Run、persona 合并器或后台服务。
已有执行模式和冻结合同必须保持；缺失模式时由当前授权与设计确定，不能静默切换。
Quick 继续以已批准 spec 为事实源，不为普通闭环任务强制创建托管状态。

Owner 从已满足依赖的任务继续，信号成立才勾选；阶段汇报、可修复测试失败和上下文
压缩不终止已授权目标。按既有 reviewer-checklist 取得必要独立视角，核实全部反馈后
在合同内整改、重测和复审。不能把自评称为独立评审，不能降低真实验收或门禁。
真实决策、不可获得权限、用户暂停和无进展熔断才需要中断；复用报告保留恢复点、
未决 finding、有效证据与资源身份。普通会话退出后不能承诺后台自动继续。
交付、环境验收、归档及 Git/发布分别遵循已有授权；未通过必测项不能宣称完整交付。

## 2. 事实源与职责分层

事实源优先级为：用户确认和原始需求 → 冻结 OpenSpec/SDD 文档 → 项目工程规则 →
托管执行合同 → 运行证据。后层只能继承和执行前层，不得重新设计前层已经冻结的内容。

- `proposal/spec/api/design/tasks/tests` 定义业务、技术实现和验收方案。
- `design.md` 必须冻结复用点、精确修改点、调用与数据流、事务并发、异常和实现顺序。
- `tests.md` 必须冻结环境、数据、启动命令、步骤、自动化命令、响应/数据库/日志断言、
  清理和证据位置。
- 实现 Prompt 只压缩并继承上述合同，不创建第二套方案。
- 托管只负责上下文冻结、调度、等待、证据、评审整改循环和终态交付。
- 口头简单需求可以生成最小执行合同；出现会改变方向的选择时必须交回 Host 澄清。

直述的 `engineering/sdd` 需求即使没有用户提供的 implementation prompt，也必须自动生成、
冻结并哈希一份**标准执行合同**后才可启动 Executor。它只约束源码核实、复用、资源所有权、
真实验收、清理、证据和澄清边界；涉及运行环境时还必须约束验收入口可移植、失败清理与
不得以宽泛替身伪造启动。直述并发需求只能要求确定性的非 5xx 业务冲突和一次持久化状态
转换，不编造具体 API、DB、事务或测试细节；这些细节仍应由项目文档或 Host 澄清冻结。
不得把“没有外部 Prompt”显示为“没有冻结合同”。

完整 Superflow 任务必须是低自由度交付：Executor 不应再决定“怎么编码”或“怎么测”。
具体 API、SQL、数据库、框架、并发和端到端测试策略不得硬编码进通用托管 Prompt。

## 3. Agent 判断与脚本裁决

脚本负责可重复、可证明、可离线重放的事实：Schema、文件、哈希、状态转换、进程身份、
命令退出码、结构化证据和协议兼容。Agent 负责需求含义、架构合理性、代码正确性、风险、
测试充分性和整改优先级。

高风险且可确定的规则不能只写在 Prompt 中，必须由 Hook、preflight 或最终门禁保障；
开放式语义判断不得伪装成正则门禁。门禁失败必须说明事实、修复入口和恢复方式。

## 4. 简单、复用与当前规范一致

- 先搜索并扩展现有模块、Skill、脚本、协议和测试，避免平行实现。
- 优先同步事务和最少状态；没有证据不得为未来扩展增加层、缓存、异步或补偿。
- 一个概念只有一个 canonical source（规范事实源）；派生资产由安装或生成流程同步。
- 协议和落盘格式要版本化、符合当前规范、失败安全、可恢复、可审计；早期项目
  不默认承诺向后兼容。缺当前必需项时阻断补齐，历史文件与未知/用户资产保留，
  保留数据不等于授予旧规范通过。
- Codex、Claude 的能力差异由适配层处理，不污染核心状态机。
- 中英文文档、Skill、Prompt、CLI 帮助和测试必须同步，语义不得漂移。

### ECC 式能力治理（默认）

每次完善 Superflow 先核对能力清单与唯一 owner：Skill Registry 负责触发和互斥，
path-scoped rules 负责项目适用范围，Hook/脚本只负责可确定的窄规则，状态仍由既有
状态机持有。先复用和收敛，再考虑新增 Skill、Hook、Prompt 或长期状态；不得用新入口
掩盖现有路由不清。安装与迁移须保持幂等、可诊断、有备份和来源证据，保留未知及用户
自定义资产。每项变化以正反例、双端安装和实际成本验证，收益不足时撤回。

### 外部项目验证隔离

外部业务项目是验证对象，不是 Superflow 的源码、依赖或内置用例库。默认复用其既有
实现和验收入口，只验证已授权范围；重新实施需求、修复业务代码或扩展环境须有用户
明确要求。确需重放时，在本仓之外的独立 checkout/worktree 执行。

原始案例、会话、详细评价、运行日志、截图、XML、探针和业务数据保存到任务专属的
仓外目录。本仓评价记录只保留去身份化的机制问题、基线、假设、合成正反例、结果口径、
结论和回滚条件；项目名、真实类/接口/表名、设备、业务提交哈希、私人绝对路径不得
成为模板、测试命名或分发资产。必要回归使用最小合成夹具，不复制真实业务工程、
依赖、配置或数据。禁止以 `.gitignore` 或不发布 docs 代替实际隔离。

收尾分别核对工作区 tracked/untracked 文件、规范资产正文及 npm 打包文件/内容；已混入
的案例材料移到仓外，受影响构建产物重新生成。只保留已证明通用且有唯一 owner 的规则，
不新增业务专用 Skill、Hook、黑名单或运行时依赖。该边界同样适用于 Codex/Claude、
中英文、项目/全局作用域；不授权修改共享资源或无关业务仓。

## 5. 安装与升级闭环

源码安装、npm 安装、Hook 自动升级必须安装同一完整能力闭包：CLI、MCP、Skill、Hook、
脚本、文档和运行时依赖。升级后必须可诊断当前版本与运行时指纹；需要宿主重启时，应在
当前会话明确通知原因和动作，不能静默使用旧进程。

## 6. 评价驱动维护

任何影响工作流或托管行为的优化，都必须遵循
`superflow-cli-evaluation-framework.md`：先记录基线和假设，再用代表性实例冒烟或回归，
最后比较交付质量、效率、成本、恢复性、人工介入和兼容性。不得仅凭单轮体感、单一耗时
或 Token 数作出架构结论。

评价器只诊断可审计事实，不替代 Host 的代码与架构语义评审。重复问题应放到正确层级：
业务实现/测试要求进入文档体系，确定性失败进入脚本门禁，语义问题进入 Host checklist，
通信与状态问题才进入托管编排。

## 7. 修改流程与完成定义

1. 阅读本纲领、评价框架和受影响专项章程。
2. 搜索现有实现，写明问题证据、责任层、变更假设和不改范围。
3. 采用最小改动，并同步中英文和三种受支持宿主。
4. 为每个独立优化准备一个代表性实例；执行受影响测试、全量测试、构建、Lint 和设计门禁。
5. 记录前后指标、异常、结论、剩余风险与回滚条件；人工批准必须区分指导、控制与预算/权限，
   不得把预算扩容漏记为零人工介入。
6. 若证据否定假设，回退或重新设计，不通过放宽测试、协议或门禁宣称成功。

完成不等于“代码已写”。只有事实源一致、职责未串层、验证通过、安装闭环完整、评价可解释
且无未声明回归时，才可交付。

## 文档连续性与执行事实（2026-10-20）

现行决策按 spec/API/design/tests 分配唯一正文 owner；详设引用行为决策并冻结
输入快照、版本来源、内容/状态写入分类、逐入口事务/代理/异常/异步及失败副作用。
冲突先回文档 owner 收敛并刷新评审与就绪引用，不把矛盾交给实现者猜。Prompt 仅为
任务/文件/用例 ID 的执行导航；SQL 内容与哈希只由 release-sql 的规范入口持有。
已有适用域决定是否加载专项合同，不以重复金额等无关模板证明完整性。

新 change 的 handoff 默认 references，仅保留规范路径、角色和既有规范化指纹；
显式 off/beta 与旧 state 保留。投影形式不改变文档身份，任务勾选/测试报告不进入
冻结合同；任务语义与设计变化仍使原就绪证据失效。

所有 SDD 执行用例必须冻结 executionEvidence: runner-captured.v1 与 executionContext，
复用现有报告 linter 实际运行构建与用例命令，保存首写盘前脱敏的输出、退出码、
实测值与版本绑定。
旧证据不升级；没有执行来源保留 PARTIAL。自洽哈希、手填 PASS 和 expected=actual
不能单独证明执行，捕获也不证明业务断言充分或抵抗本机恶意篡改。

独立 Reviewer 的实际派发、隔离范围、输入 diff、报告与 finding 复评记录放在既有
报告中。身份字段不是独立性的防伪签名；缺独立能力如实保留缺口并继续其余授权工作。
修复后旧 PASS 不覆盖新增影响，完整交付须对账目标、实测、复评、外部协同与资源。

## 阶段承接与当前交付闭环（2026-10-21）

总入口保持短路由，完整旧细则保留按需参考；当前阶段Skill与必读规范必须实际读取，
不能用入口摘要代替。修文档冲突须改canonical正文及消费引用，不只是选优先级或刷hash。

所有 SDD 准入与续跑统一要求 workflowPolicy: observed-delivery.v1，声明的执行用例
必须冻结 runner-captured.v1 与 executionContext。现有 coding-ready owner 裁决当前要求；
缺项保留历史文件并写 BLOCKED，由文档 owner 补齐与重新评审，不授予旧 READY 豁免。
所有 PASS receipt 都必须实际 capture，旧证据仅作历史或 PARTIAL。

所有完整 SDD 验证沿现有report linter引用实际独评/复评报告，核当前状态、明确无未决
Findings及Reviewed Sources身份清单；修后源码变化使旧报告失效。清单是收到的输入
身份，不等于全仓逐字评审；真实diff/读取范围、Reviewer独立性与结论充分性由Agent
核验。修复、缓解、授权延期和不成立分别记录，不能以日志改善替代功能修复。

仍复用原文档、四状态报告、Coding Ready与三种托管消息，无新Task/Run、Hook或
代理能力限制。原生非SDD请求不因此增加研发合同；暂停/恢复和Git授权与业务指导分列。

## 日常自动更新默认策略（2026-10-22）

现有依赖更新 Hook 在未设置或留空模式时默认 apply，显式 check 只提示，off/0 关闭。
复用同一 update owner、会话去重、全局六小时节流和互斥锁；失败保留日志并释放
节流资格供后续会话重试。成功后提示重启，不把磁盘更新当作当前宿主热加载。

## 交接导航、追溯与独评闭环（2026-10-22）

实施主Prompt引用公共canonical合同，批次仅导航主Prompt及本批任务/入口/用例；
公共约束由同一主入口消费，不能靠每批重复合同正文证明继承。已声明导航与既有
coverage/task索引闭合，入口全集和真实载荷仍由Agent源码调查及独评判断。

原独立评审保留状态、finding ID和内容身份；Owner处置另记，不覆盖原Reviewer结论。
有问题的交付需实际复评关联原报告/处置及逐finding结果；当前报告绑定当前源码，
历史报告保留历史输入身份。DONE不能残留未决Concerns。文件hash/派发引用只证明
记录身份，不证明独立性、真实阅读或修复正确；Host继续语义核验。

运行test-report不参与canonical hash，在所有context_compression模式只引用而不投影正文；
不能为保留旧投影而增加围栏猜测或平行正文解释器。
