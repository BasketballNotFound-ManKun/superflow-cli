# 0.5.10：需求到真实入口的交付防漏评价

## 问题证据与责任层

事故的需求已经允许子账号继续创建账号，但要求保持同一主账号归属。
后续文档把一个已登记创建入口按“不适用某类过滤”整体排除，开发与测试围绕另一条
正确入口自洽，实际页面按角色走旧入口。复盘初期又曾把允许动作误建议为拒绝。
这是来源语义保真、逐维度排除审查、真实入口验收的组合缺口，不是要求用户写更多技术细节。

责任放在现有文档评审、Coding Ready 和验收 Skill，不改业务项目，不另建托管状态机。
框架只保留通用需求/入口/来源/用例结构；账号案例只出现在回归夹具，不写入运行时业务规则。

## 基线与假设

- 0.5.9 基线全量：79 文件、551 测试通过；本机耗时 82.43 秒。
- 旧文档审计验证三种 lens、handoff 标记和 prompt 链接，没有需求×入口覆盖索引。
- 旧启动/Hook 仅比较凭证与 state 的 hash 字符串，不重算文档；失败的 coding-ready
  不替换此前 READY。
- 假设：扩展现有凭证、复用 handoff 规范化与来源指纹，可阻断缺漏和过期凭证；
  语义错误由独立原文反查负责，而不是脚本猜测。代价是旧文档须一次性补齐复审。

## 语义评价边界

本轮主 Agent 对照事故原文和新合同独立复核了两个错误方向：
“允许创建但限定归属”不能翻译为“拒绝”；“不适用某过滤”不能排除其它业务维度。
中英文 docs、requirement-review、verify 都强制读取同一结构的审查说明。
这不是新一轮真实业务执行，也不是跨模型语义基准。未重新运行充电系统页面/数据库验收，
不声称业务 Bug 已修复，不声称以后所有 Agent 都能被确定性脚本证明理解正确。
来源清单完整性、排除理由是否真实、断言是否足够、执行证据是否忠实仍须 Agent 审查。

托管三种通信协议、状态机、预算、恢复、资源清理均未改变；口头最小合同路径不加
文档 coverage 要求。旧已启动 Run 恢复不重建合同；若原生 Hook 遇旧 receipt，需补齐复审。
新增成本是派发前一次本地 handoff 重算和文件指纹检查，没有新增模型调用或轮询。
没有可比的真实任务 Token、人工介入或耗时样本，不能报告这些指标已改善。

## 结论与回滚条件

结构性漏项与内容漂移防护有效；语义质量改进仍待后续真实任务观察。
若正确合同持续被误阻断、安装布局漏部署、跨平台重算不一致或正常进度被误判漂移，
停止升级推广并回滚运行时到上一版本，保留新评审证据；不得删掉证据或绕过门禁求绿。
后续统计需求反转/排除误判、首轮通过率、人工方向纠正次数和复审开销，再决定是否扩展。
